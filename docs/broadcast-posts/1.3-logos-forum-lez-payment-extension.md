## TL;DR

The A2A protocol deliberately omits payment — implementers are expected to layer their own settlement. Google shipped [`a2a-x402`](https://github.com/google-agentic-commerce/a2a-x402) (HTTP 402-based) for HTTP transports; there's the [AP2 (Agent Payments Protocol)](https://github.com/EmilLindfors/a2a-rs/tree/main/a2a-ap2) extension framework gaining traction.

This proposal defines an A2A extension for LEZ-native payment: per-task settlement in LEZ tokens, with three modes — shielded (default, full ZK private), transparent (lower latency), or escrow (atomic-on-completion via a `task-escrow` LEZ program).

Spec (v0.1 draft):
**https://github.com/warfield2016/logos-agent/blob/main/spec/lez-payment-extension.md**

Canonical extension URI:
`https://logos.co/spec/a2a-extensions/lez-payment/0.1`

## What's in the spec

- Skill pricing in AgentCards (per-skill `price_lez` field, `u128`-string-encoded for precision)
- Three settlement modes (shielded / transparent / escrow)
- Payment envelope schema: `Commit { tx_hash, settlement }`, `Receipt`, `Refund`
- Provider-side verification flow (on-chain check before WORKING transition)
- Cancellation + refund semantics
- **Inverse income threshold** — provider-side cap that auto-rejects above-threshold payments. Useful for anti-grooming and rate-limiting (the spec text covers this; reference impl in `crates/agent-core/src/spending_policy.rs` with passing tests)
- Compatible with both the canonical HTTP transport and the [Logos Messaging binding](LINK-TO-1.2-POST)

## What I'd like feedback on

1. **Single token vs multi-token.** v0.1 limits to one token per AgentCard. Real demand for multi-token pricing in 0.2?
2. **Escrow program ABI.** I've sketched `open / complete / cancel / dispute / resolve`. Does this overlap with anyone's WIP, particularly LP-0002 (Private M-of-N Multisig)?
3. **Refund policy declaration.** Provider-defined and surfaced in AgentCard `extensions[0].params`. Is that the right place, or should it live elsewhere?
4. **Income cap semantics.** Per-day per-token. Should it also support per-counterparty caps?

## Context
